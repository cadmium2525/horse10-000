# 10,000 HORSE RACE — ゲーム設計書 v1.0

作成日: 2026-10-25  
対象: GitHub Pages / Three.js / スマートフォン・PC / 運用費0円

## 1. 企画の結論

**「9,999頭を抜け。馬の山を跳び越えろ。」**

10,000頭が同時に走る、コミカルな物理演算サバイバルレース。プレイヤーは最後方の1頭を操り、密集した集団の隙間を抜け、転倒連鎖による馬の山をジャンプで越え、1位を目指す。馬は負傷・流血せず、玩具のように弾んで転がり、すぐ起き上がる。

設計原則:

1. 数の暴力が画面で即座に伝わる。遠景まで「馬だらけ」。
2. 簡単な操作（左右・ジャンプ・短時間ダッシュ）で上達できる。
3. 大転倒は予測可能な危険であり、同時に近道のチャンス。
4. 順位は演出用の数字ではなく、競走状況から一貫して算出する。
5. 1プレイ約60～90秒、スマホ横持ちを第一候補として検証する。
6. 結果の画像が自動生成され、手軽に保存・共有できる。

### ターゲット

- ブラウザで短時間遊びたい人、SNSのゲーム動画を見る人
- レースやラグドール系のカオスな物理挙動を楽しみたい人
- スコアを競い、1位・ノーミスを目指したい人

### 成功指標（開発仮説・計測可能時の目安）

- 初見10秒以内に「1万頭レース」と「1位を目指す」ことがわかる
- スマホ実機で入力遅延を感じず、再挑戦したくなる
- 15秒以内に最初の大規模転倒、30秒以内に大きな順位変動を経験
- 結果画面からカード保存と投稿導線に2タップ以内で到達

## 2. MVPゲームルール

| 項目 | MVP仕様 |
|---|---|
| 出走数 | プレイヤー1頭＋NPC 9,999頭。モデル表示は端末性能に応じてLOD化 |
| 初期順位 | 10,000位（全員の走行進捗にわずかな差を設定） |
| 勝利 | ゴールラインを最初に通過する（1位） |
| PERFECT | **1位かつ転倒0回**。単なる1位と区別する |
| 記録 | 順位、タイム、追い抜き数、転倒数、最大連続追い抜き、シード |
| リトライ | 1ボタンで同シード再挑戦／別シードで新レース |
| 障害 | NPC衝突、転倒した馬、馬の山、混雑した進路 |
| ダメージ | 体力・死亡なし。転倒は約1～2秒ロスして自動復帰 |
| 失格 | なし。最後まで走れる。タイムアウトの場合も順位を結果として表示 |

順位定義: 各馬の前進進捗 `progress` を基準に、ゴール前は `rank = 1 + count(npc.progress > player.progress)` とする。同値時は安定した馬IDをタイブレークに使う。ゴール後はゴール時刻で確定。追い抜き数は「そのレースで初めて前に出た異なるNPC数」で最大9,999。順位の増減と追い抜き数は別の統計とする（再追い抜きによる水増し防止）。

**ゲーム性の注意:** 1万頭を狭いコースで一斉に実物サイズで走らせると、通行不能になる。MVPは非常に広いコースと複数の走行帯を持つ「異常な規模の架空競馬場」。先頭・中団・後方の密度を設計し、頻繁なオーバーテイクと接戦が両立するよう調整する。プレイヤーだけ過剰に速いゲームにはせず、ジャンプの正確さと進路判断で有利を得る。

## 3. プレイループと画面

1. **タイトル:** 『10,000 HORSE RACE』、背景で大量の馬が走る。「レース開始」「遊び方」「音設定」。
2. **出走演出（3秒）:** 超広角で1万頭を見せる → プレイヤー後方カメラへ。`10,000位 / 10,000頭` を大きく表示。
3. **レース（60～90秒目標）:** 進路取り、ジャンプ、ダッシュ、衝突、転倒連鎖、馬の山の跳び越え。
4. **終盤（残り約10秒）:** 先頭集団を強調。順位・残り距離を主役にする。カメラの過剰な揺れは抑える。
5. **フィニッシュ:** 順位とタイム確定。1位はWIN、1位かつ転倒0ならPERFECT演出。
6. **リザルト:** 結果カードを表示。「画像を保存」「共有」「Xで投稿文を開く」「もう一度」。

### カメラとHUD

- 通常は後方追従3人称。ジャンプ中はやや引き、着地点が見えることを優先。
- 左上: 現在順位 `1,248 / 10,000`。右上: 残り距離／タイム。
- 中央上部: 小さな進捗バー。下部: ダッシュ残量とジャンプ操作。
- 大量追い抜き時: `+582 頭抜き！` を短時間表示（実データに基づく）。
- 危険な転倒群は遠方から砂埃・色・地面マーカーで予告。
- 強いカメラ揺れ、点滅、モーションブラーは設定で軽減／OFFにできる。

## 4. 操作とレース物理

| アクション | スマホ横持ち | PC |
|---|---|---|
| 左右移動 | 画面左側をドラッグ／仮想スティック | A/D、←/→ |
| ジャンプ | 右側大ボタン | Space |
| ダッシュ | 右側小ボタン長押し | Shift |
| ポーズ | 上部ボタン | Esc |

ジャンプ: 1回押すと固定ジャンプ。空中で二段ジャンプはできない。着地点の混雑・転倒体と衝突すると失敗する。クールダウンあり。ダッシュ: 約2秒発動、ゲージ消費、自然回復。ダッシュ中も衝突無敵にはならない。

### NPCの挙動

NPCは `RUN / AVOID / STUMBLE / FALL / RECOVER / FINISH` の状態を持つ。近距離ではレーン変更、回避、接触・転倒、起き上がりを扱う。転倒は近傍NPCに衝突インパルスを伝え、転倒連鎖が生じる。一定距離内でしか詳細な衝突判定をしない。転倒確率には速度差・接触角度・密集度・足元状況を反映し、単なるランダム抽選だけにしない。

### 転倒連鎖の安全設計

- 危険が見えてから避けられるまで最低約1秒の猶予を目標とする（調整値）。
- 馬の山は低い部分ならジャンプ可能。高すぎる部分には迂回路を残す。
- プレイヤー直前に不可避の山を突然生成しない。
- 転倒はコメディ的なラグドール風。流血、骨折、苦痛演出なし。
- 実際のバグで進路が完全封鎖された場合はNPC集団の解消処理を行う。
- 難度調整で「事故頻度」と「回避余地」を独立して調整する。

## 5. 10,000頭をスマホで動かす実装方式

**重要: 10,000頭すべてを剛体＋骨格アニメーションで物理演算しない。** 見た目は10,000頭、計算は段階的に近似する。品質とFPSを確認しながら調整する。

| 層 | 想定頭数の目安 | 表現・更新 |
|---|---:|---|
| A: ごく近距離 | 約30～80 | 簡略コライダー、個別転倒挙動、低ポリ馬、脚アニメ |
| B: 中距離 | 約300～800 | 簡易状態機械＋近接判定、`InstancedMesh` 表示 |
| C: 遠距離 | 残り約9,000 | 集団フロー・位置データを低頻度更新、インスタンス表示または疑似群衆 |

※数字は初期予算であり固定保証ではない。低性能端末では同時可視頭数を減らし、遠景は代理表現に置換。ただし全9,999 NPCのレース進捗とIDは保持する。

### 描画

- Three.js `InstancedMesh` で同一形状・材質の描画呼び出しを抑える。近景のみ個別メッシュで高品質化。
- 低ポリの馬を基本。胴・頭・脚・騎手を最小形状に分割し、近景のみにアニメーション。
- 遠景はLOD、フラスタム／距離カリング、集団の粒状表現を適用。
- 空・芝・トラックは軽量材質。影はプレイヤー周辺限定、遠景は疑似影。
- ピクセル比を端末負荷で動的変更。フルスクリーン・横持ち推奨UI。

### シミュレーション

- 固定時間刻み（例: 30Hz）の決定論的なゲーム更新と可変描画FPSを分離。
- プレイヤー周辺だけ空間ハッシュで近傍候補を探索。全NPC総当たりの O(N²) 判定は禁止。
- 遠方NPCは統計モデル／簡易速度曲線／群れ単位のイベントで進捗を更新。
- 近景へ入った個体は位置・速度・状態を引き継ぎ、表示上のテレポートを防ぐ。
- 転倒イベントが近景から遠景に波及するときは、集団イベントとして軽量に解決する。
- 同一シード＋同一入力ログで結果を再現できることを目標にする。ただし異なる端末・浮動小数点環境での完全一致は別途検証。

### 性能目標と検証

- 主要スマホで30FPS安定を第一目標、PCは60FPS目標。
- 低性能端末は自動画質変更。開始前に簡易ベンチで描画レベルを選ぶ。
- 順位更新は毎フレーム全件ソートしない。進捗差分または低頻度集計（例: 5～10Hz）で十分。
- 長時間使用時の発熱、GPUメモリ、メッシュ更新コスト、ページ復帰時の安定性を実機確認。
- スマホでゲームが止まらないことを画質より優先。

## 6. リザルトカードとX投稿

**目的:** カード単体を見ただけで「1万頭のレースで何位だったか」が伝わること。

### カードデザイン

- 推奨画像: 1200×630px（横長シェア用）および1080×1350px（縦長保存用）の2形式。
- 画面: 走り抜ける馬＋背景の膨大な集団＋大きな順位数字。
- コピー: `10,000 HORSE RACE` / `9,999頭を抜け！`
- 主要情報: `順位 1 / 10,000`、`追い抜き 9,999頭`、`タイム 01:12.34`。
- 補足: `転倒 0回`、`PERFECT` バッジ、日付、レースシード、短縮したプレイURL。
- 色分け: PERFECT 金／1位 青／その他 白。過剰なエフェクトは数字を隠さない。
- チート対策上、カードはユーザー端末生成の**自己申告記録**と明示できるようにする。サーバー検証ランキングを装わない。

### 共有ボタン（静的サイトのみ・無料）

1. **「結果画像を保存」:** ゲーム終了時の専用Canvasへ結果を描画し、PNGとしてダウンロード。DOM全体のスクリーンショットに依存しない。文字は埋め込みフォントを利用。
2. **「画像を共有」:** `navigator.canShare({files:[file]})` が有効なら、`navigator.share({files:[file], text, url})` でOS共有シートを開く。Xが共有先に出るか、画像が添付されるかは端末・ブラウザ・アプリに依存する。
3. **「Xに投稿」:** `https://twitter.com/intent/tweet?text=...&url=...` のWeb Intentを開き、テキスト＋ゲームURLを事前入力する。**この方法だけではローカル生成PNGを自動添付できない。** カード保存・画像共有を隣に置き、「保存画像をXで添付してください」と案内。
4. **フォールバック:** Web Share API非対応時は画像保存＋投稿文コピー＋X投稿文起動を提供。

推奨投稿文例:

> 🐎 10,000頭競馬に挑戦！  
> 🏆 1位 / 10,000頭  
> 💥 追い抜き9,999頭・転倒0回  
> #10000HorseRace  
> ［ゲームURL］

### シェアから再プレイの導線

- カードには「挑戦してみる」URLを明記。クリック可能な投稿本文にも同URLを含める。
- `?seed=xxxxx` をURLで受け取り、同じコースで友達が挑戦できるようにする（プレイヤー操作は異なるため同結果を保証しない）。
- 通常のGitHub Pagesではユーザーごとに動的OGP画像を生成できない。投稿文のURLプレビューは固定OGP画像とし、個人記録はPNGの手動／OS共有に頼る。
- X API認証、自動画像投稿、サーバーサイド画像生成はMVP対象外（無料・静的構成を守る）。

## 7. 技術構成・ディレクトリ

| 領域 | 採用 |
|---|---|
| 言語 | TypeScript |
| ビルド | Vite（静的ビルド） |
| 描画 | Three.js / WebGL |
| UI | HTML/CSSオーバーレイ（Canvas HUDでも可） |
| 物理 | 独自の簡易球／カプセル衝突＋転倒アニメ。初期は外部物理エンジン不要 |
| 音 | Web Audio API、ライセンス確認済みの自作／無料音源 |
| 保存 | localStorage（設定・自己ベスト・最近のシード） |
| 配信 | GitHub Pages、GitHub Free の**公開**リポジトリ |
| 課金・サーバー | なし |

```text
10000-horse-race/
  public/
    assets/                 # 圧縮した3Dモデル・音・固定OGP画像
  src/
    main.ts
    game/Game.ts            # 状態遷移とゲームループ
    game/Race.ts            # 順位、進捗、ゴール処理
    game/HorseSimulation.ts # NPC状態と遠近LOD更新
    game/Collision.ts       # 局所的な接触・転倒連鎖
    game/PlayerController.ts
    render/World.ts         # Three.jsシーン
    render/HorseLOD.ts
    ui/Hud.ts
    ui/Result.ts
    share/CardRenderer.ts   # Canvasによるカード描画
    share/Share.ts          # Web Share/X intent/保存
    data/Seed.ts            # 再現可能なコース生成
    styles.css
  index.html
  vite.config.ts
  package.json
```

Viteは `base: '/<repository-name>/'`（ユーザー／組織サイトなら `/`）を設定し、静的ビルド `dist/` をGitHub ActionsからPagesへ公開。ルーティングは基本的に単一ページ＋クエリパラメータ。外部APIキーや秘密情報をクライアントへ埋め込まない。

## 8. 開発・運用コスト0円の範囲

- GitHub Freeの公開リポジトリ＋GitHub Pagesを利用。Pagesは静的配信で、サーバー処理は持たない。
- Three.js、Vite、TypeScript、ブラウザ標準APIを利用。購入アセット・有料解析・広告SDKを導入しない。
- アートは自作の低ポリモデルとシンプルなマテリアルを基本にし、第三者音源・画像のライセンスを記録する。
- 独自ドメインは不要。GitHub PagesのURLを使用。
- **無料枠には利用上限・利用規約がある。** 大規模アクセス時の配信・Actions使用量は確認する。「必ず永遠に無料」を保証するものではない。
- サーバーがないため、不正防止付き世界ランキング、オンライン同期、友達対戦、SNS自動メディア投稿はMVPでは実装しない。

## 9. 段階開発と受け入れ基準

### Phase 0 — 技術検証（最優先）

- 10,000頭相当の見た目を描画。低ポリ／インスタンス／LODの実測。
- スマホでカメラ追従・描画負荷・タップ遅延・発熱を確認。
- 30～50頭の局所的な衝突、転倒連鎖、復帰を再現。
- **中止／設計変更基準:** 実機で30FPSに届かず、視認性の改善余地も乏しい場合は表示手法・レース規模表現を見直す。

### Phase 1 — 遊べる縦切り（まず100頭）

- 100頭＋プレイヤー、左右移動・ジャンプ・ダッシュ。
- 接触転倒、順位更新、ゴール、再挑戦。
- 馬の山が危険かつ利用可能なショートカットになることを確認。

### Phase 2 — 10,000頭レース

- 複数LODと遠景集団シミュレーションを統合。
- 10,000頭の固有ID・進捗を管理し、順位・追い抜き数の整合性をテスト。
- 難易度カーブ（大量追い抜き→回避→先頭戦）を調整。
- 事故が頻発してもフリーズ、完全封鎖、永久転倒が発生しない。

### Phase 3 — リザルト・共有

- Canvasカードを2サイズで生成。PNG保存。
- Web Share APIのファイル共有・X Web Intent・コピーのフォールバック。
- iOS Safari / Android Chrome / PC Chrome・Firefoxで確認。
- URLシードで同じコースを再生成。ゲームURLのコピー機能。

### Phase 4 — 公開前QA

- GitHub Pagesのサブパスで全アセット読込成功、HTTPS、初回ロードを確認。
- 低・中・高性能スマホでFPS、操作感、長時間発熱、端末回転、ブラウザ復帰。
- `1位・転倒0` のみPERFECT。タイムアウト／途中終了／同着の扱いが正しい。
- 全てのボタンが動く。共有不能時にも画像保存とコピーが残る。
- 投稿カード内の数値がゲーム結果と一致する。

## 10. 設計上のリスクと判断

| リスク | 対策 |
|---|---|
| 10,000頭のリアルタイム剛体計算は重い | 近傍のみ物理、遠景は状態・集団モデル、InstancedMesh |
| 画面が馬で埋まって走れない | 幅広コース・走行帯・局所密度制御・前方可視性 |
| ランダム事故で理不尽に負ける | 早期予告、ジャンプ・迂回、復帰、必ず回避可能なルート |
| 大量追い抜きが数字だけの演出になる | 固有NPC進捗と順位を管理。表示の大群とデータを一致させる |
| リザルトPNGをX投稿画面へ自動添付できない | Web Share APIを第一候補、保存＋投稿文Web Intentを確実な代替手段に |
| 無料運用に限界がある | 静的ファイルのみ・軽量アセット・無課金構成、利用規約に従う |
| 完全ランダムで腕前が反映されない | 同シード再挑戦、読める危険、入力による回避・ショートカット |

## 11. MVPで作らないもの

- 10,000体すべての厳密な骨格＋ラグドール物理
- マルチプレイ、サーバーランキング、アカウント、課金
- キャラクター育成、馬の購入、ガチャ
- 無許諾の競走馬名・著名ブランド・既存ゲームアセット利用
- X APIを使った投稿代行や自動画像添付

## 12. 最初に決めるべき3つ

1. **アート方向:** 丸みのあるローポリ・玩具風（推奨）。転倒が残酷に見えず、描画も軽い。
2. **コース方向:** 直線主体＋緩いカーブ（推奨）。混戦の視認性が高く、最初の試作が容易。
3. **端末方向:** 横持ち基準（推奨）。視野が広く、回避操作とHUDが成立しやすい。縦持ちは可能なら別レイアウトで対応。
